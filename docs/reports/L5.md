# L5: Route A (Python service beside Unity) feasibility

## 1 Verdict: GREEN
Transport cost is negligible: 51 KB response round trip is ~0.04 ms on loopback (VERIFIED). The actual cost is GPU inference and the TensorRT plan build, both outside the transport. The service route needs no native plugin and works with plain `System.Net.Sockets`. Caveat: it needs a CUDA machine for the engine (docs: engines "need a CUDA device", VERIFIED), and Unity 7000.0.0a12 behavior was not tested in-editor.

## 2 Answers
1. **Pick TCP, length-prefixed binary, on 127.0.0.1.**
   - `System.Net.Sockets` ships in Unity's .NET profile, no package, no DLL, no native plugin (INFERRED from Unity docs knowledge; not run in a12). The a12 editor is installed at ~/Unity/Hub/Editor/7000.0.0a12 (VERIFIED) but I did not launch it.
   - NetMQ: pure managed but a NuGet import into an alpha editor; adds nothing over TCP for a 1:1 link (INFERRED). gRPC: Unity support is poor, HTTP/2 and Grpc.Core native libs are the pain (INFERRED). WebSocket: extra framing, no benefit locally. Shared memory: needs a sync primitive and platform code, and the gain is microseconds that do not matter (VERIFIED by measurement below).
   - Domain reload: sockets die on reload. Own the connection in a static class with `[InitializeOnLoad]` plus `AssemblyReloadEvents.beforeAssemblyReload` to close it and reconnect afterwards. The Python process lives independently and keeps its GPU engine loaded. A stateless protocol (context sent every request) means reconnect loses nothing (INFERRED, design choice).
2. **Payload** (VERIFIED arithmetic, 4 B floats). Pose = 30x7x4 = 840 B. Frame = 840 + root 28 + contacts 16 = 884 B (if root is already joint 0, 856 B).

| Item | Bytes |
|---|---|
| Response, 18 frames | 15,912 |
| Response, 58 frames | 51,272 |
| 3-target sequence, worst case 3x58 | 153,816 |
| Request, 4 context + 4 target poses | 6,720 |
| Request, 3 targets with 4 poses each | 13,440 |
| Steady stream at 30 Hz | ~26.5 KB/s |

   f16 option halves it; unnecessary.
3. Measurements are in section 3.
4. **Editor responsiveness:** keep the socket read on a background Task, never block in `EditorApplication.update`. Receive thread decodes into a pooled `float[]`/`NativeArray` and enqueues a result in a `ConcurrentQueue`. A main-thread pump (`EditorApplication.update`, or `Update` in Play mode) dequeues and applies. Tag each request with `request_id`, and drop results whose id is stale. Handle `EditorApplication.playModeStateChanged` (cancel in-flight, drop queue, bump an epoch counter) and `beforeAssemblyReload` (close socket, cancel the task via CancellationToken). Use a connect timeout and heartbeat PING so a dead service shows a status, not a hang. (INFERRED; standard Unity pattern, not run in a12.)
5. **Schema:** reports/L5/schema.md. Binary header (magic, version, type, request_id, body_len) then fixed layout. Request holds config, 4 context poses, targets with `num_poses_to_use`, `transition_early_by_frames`, token-count override, IK mask. Response holds `num_frames`, frames, foot contacts, and timing. Fields mirror runtime_api.md (VERIFIED against the doc).

## 3 Measurements (VERIFIED, loopback, TCP_NODELAY, this machine, 12 cores)
Stub server: Python asyncio, echoes zero-filled payload. Request 13.5 KB. 500 samples after 50 warmup.

| Client | 18 frames (15.9 KB) | 58 frames (51.3 KB) | 3 x 58 sequential |
|---|---|---|---|
| Python socket, median / p99 | 0.038 / 0.067 ms | 0.043 / 0.076 ms | 0.135 / 0.188 ms |
| .NET 8 async socket, median / p99 | 0.041 / 0.077 ms | 0.041 / 0.068 ms | 0.122 / 0.177 ms |

Not measured: real model compute, Unity's Mono/IL2CPP socket path, serialization into Unity types.

## 4 Conflicts
- The brief says "30 joints x position+quaternion, plus root". The doc's SOMA pose already has the root as the first joint (VERIFIED), so a separate root is only needed if you want world-space root. Schema carries it explicitly (+28 B/frame).
- The doc says G1 uses 36 joint coordinates, not 30 joints. The schema is SOMA-first; G1 needs a different pose size (INFERRED, flagged via the `rig` byte).

## 5 Unknowns
- Real generation latency (GPU, not available here); decides whether per-target chaining at 30 Hz is feasible.
- First-run TensorRT plan build takes "a few minutes" (doc, VERIFIED), so the service needs a ready-handshake.
- Whether Unity 7000.0.0a12 Mono/IL2CPP handles background Tasks and `Socket` identically to 6.x; untested.
- Coordinate-space conversion (Y up SOMA vs Unity left-handed Y up) belongs on the Unity side or service; not decided.

## 6 Risks
- Stale context: chained generation requires the actually-played poses; Unity must send them each time or the character jumps (doc, VERIFIED).
- Domain reload mid-request loses the response; mitigated by request_id and idempotent retry.
- Alpha editor instability around reload hooks (INFERRED).
- Python process lifecycle: orphaned processes holding the GPU; add parent-PID watchdog and a port-in-use check.
- Firewall or port clashes on localhost; use a configurable port and an ephemeral fallback.
