# L1 report: MotionBricks SOMA feasibility (RTX 3060)

Repo `~/GitHub/motionbricks` at v0.2.0. GPU: `nvidia-smi` shows NVIDIA GeForce RTX 3060, 12288 MiB, driver 615.78.08, sm_86. VERIFIED. TensorRT 10.8.0.43. No repo files edited. FP16 plan built into a scratch cache.

## 1. Verdict: GREEN
Array-in, frames-out works in a plain Python process: deterministic, about 4.7 ms (FP32) or 2.5 ms (FP16) per call. Gaps: no SOMA file writer, no thread safety, and you must build the 77-joint skeleton yourself.

## 2. Answers

**Q1. Minimal call sequence.** VERIFIED (ran it on arrays). Source: docs/examples/generate_once.py:28-64, _rig.py:51-61.
```python
wp.init(); wp.set_device("cuda:0")
skel = load_skeleton_from_usd(get_asset_file("human","soma_base_skel_minimal_no_root.usd"), SOMA_SKELETON_PRIM_PATH)  # _rig.py:54
m2r = SpaceConverter(FacingDirectionType.MUJOCO).convert_transform(wp.transform_identity())                         # _rig.py:59, or identity
with MotionBricksSOMAEngine(SOMA_N1_FP32_ONNX_PATH, model_to_runtime=m2r) as eng, wp.ScopedStream(eng.stream):
    ctx, tgt, out = eng.create_input(skel), eng.create_input(skel), eng.create_output(skel)
    ctx.update_from_poses(wp.array(np_ctx, dtype=wp.transform), stream=eng.stream)   # np (4,77,7) f32
    tgt.update_from_poses(wp.array(np_tgt, dtype=wp.transform), stream=eng.stream)   # np (1..4,77,7)
    eng.generate_animation(ctx, tgt, out, config=None)     # model/engine.py:330, blocks until done
    frames = out.poses[:out.num_frames].numpy()            # (n,77,7); out.foot_contacts[:n] -> (n,4)
```
Chaining: feed the last 4 output poses back as the next context (generate_once.py:63). Arrays-in was tested with `wp.array(np (4,77,7) float32, dtype=wp.transform)`.

**Q2. Pose layout.** VERIFIED from code and runtime dumps.
- Joints: `soma_n1.json` lists 30 model joints, `Hips` first: Hips, Spine1, Spine2, Chest, Neck1, Neck2, Head, Jaw, LeftEye, RightEye, LeftShoulder, LeftArm, LeftForeArm, LeftHand, LeftHandThumbEnd, LeftHandMiddleEnd, RightShoulder, RightArm, RightForeArm, RightHand, RightHandThumbEnd, RightHandMiddleEnd, LeftLeg, LeftShin, LeftFoot, LeftToeBase, RightLeg, RightShin, RightFoot, RightToeBase.
- The engine does not take these 30 in this order. It takes the 77-joint USD skeleton, matched by name (soma/engine.py:94-106). Model joint i sits at skeleton index [0,1,2,3,4,5,6,8,9,10,11,12,13,14,18,28,39,40,41,42,46,56,67,68,69,70,72,73,74,75]. The skeleton may have extra joints (fingers). It needs the root at index 0 and parents before children (true for the USD skeleton).
- Per joint: wp.transform = 7 floats `[px,py,pz, qx,qy,qz,qw]`, quaternion XYZW, meters. All joints are local (parent-relative). Joint 0 (Hips) has no parent, so its local transform is its world transform in runtime space. Non-root translations are bone offsets and do not matter beyond the skeleton reference.
- Model space is Y up (soma_model.md:91). `model_to_runtime` is a 90 degree rotation about X (space_conversion_utils.py:30), giving Z up. The engine default is identity, so Y-up input works with no conversion.
- Root handling: the engine strips the last context pose's ground XZ position and heading (heading from RightLeg/LeftLeg, kernels.py:14-25, 55-78) and keeps height. Afterwards it re-applies the alignment and `model_to_runtime` (kernels.py:211-217). Output starts at the last context pose and ends at target pose 0.
- Output: 18-58 frames at 30 Hz (26 in my test). Foot contacts are [n,4] in 0..1.
- Model joints 14, 15, 20, 21 (hand-end joints) keep the reference pose, because their parents are not model joints (verified at runtime).

**Q3. Determinism.** VERIFIED. Bitwise identical in both precisions and in all four cases tested: repeated calls in one engine; after a different intermediate request; across separate processes; foot contacts too. FP32 and FP16 differ from each other on the same input: max abs 0.094 on quaternion components, root position 2.7 mm, foot contacts 0.092. The docs warn they can pick different tokens (runtime_api.md:122). No sampling or RNG was seen in the code path (INFERRED from reading).

**Q5. One long-lived process.** Engine reuse and CUDA graph: VERIFIED (about 650 calls per process on one engine, stable GPU memory, graph baked on first call, engine.py:359). Thread safety: INFERRED not safe. Every call mutates engine-shared device buffers (`_alignment`, `_generated_frame_count`, TensorRT I/O) and the shared `out`; there are no locks (grep: only progress.py). Use one engine plus a request queue, or one engine per worker (about 1.6 GiB each).

**Q6. Correction.** VERIFIED by diffing against `correct_generated_diff=False`.
- `correct_generated_diff` is `_post_process_generated_poses` (soma/engine.py:198-220, kernels.py:244-317). It runs on the GPU inside `generate_animation` (engine.py:365). It moves frame 0 onto the last context pose and the last frame onto target pose 0, spread linearly over the frames.
- Measured: root moved 3.8-7.9 mm and 1.6 deg; start/end root error went from 5/8 mm to 0.
- Non-model joints (fingers etc.) get reference pose raw. With correction they are blended from context to target, up to 34 deg in my test (the clip carries finger motion). Non-root translations shift by up to 4.7 mm, because the correction also blends the translations of the supplied context and target.
- Foot contacts are unaffected (the correction touches poses only; INFERRED).
- The IK pin corrector (`TargetPoseIKCorrector`, runtime/target_pose.py:166-300) is NOT in the engine. It is optional app code: character.py:296-301 calls it on the sampled playback pose, weighted by smoothstep over the last part of playback (character.py:277-285). It two-bone-IKs hands and feet onto the target. It is off unless `ik_pin_mask` is set, so a raw `generate_animation` output has none of it. To bake it you must call `capture_pins` and `apply` yourself per sampled frame. I did not run it (INFERRED from reading).

**Q7. Saving.** No SOMA writer exists. VERIFIED by grep: only `save_csv` (io/csv.py:75), for G1; `load_bvh` has no matching saver; app/ has document savers only. The `AnimationBuffer.poses[:n].numpy()` array is the easiest thing to dump. Writing BVH or USD means writing your own exporter (Euler conversion and the skeleton hierarchy).

Docs claim for 4090: 2.50 / 1.28 ms; the 3060 is about 1.7x slower. Other processes held 899 MiB at the start. `docs/examples/generate_once.py` ran in 7.7 s wall and printed 26 and 50 frames. Use `.venv/bin/python`.

## 4. Conflicts
- soma_model.md:130 and onnx_inference.md list only 4090 / Windows as tested. This run is Linux / 3060, and the outputs are sane.
- soma_model.md:7 and the manifest name 30 joints, but the engine needs the 77-joint skeleton (soma/engine.py:94-106). Not a real conflict; the 30 joints are a subset matched by name.
- TensorRT logs "plan file across different models of devices" on every load, including a plan the cache JSON says was built on the 3060. Cosmetic in my runs.

## 5. Unknowns and fastest way to settle
- Thread safety under concurrent calls: run two threads against one engine and compare with the serial output (5 min). I only read the code.
- IK corrector output: run `capture_pins` and `apply` on one frame and diff (10 min).
- FP32 cold build time: delete or force-rebuild into a scratch cache (about 2 min, if it matches FP16).
- Whether a skeleton trimmed to 30 joints works: build one with `Skeleton(...)` and call `create_input`. Hand-end joints would need re-parenting.
- Motion quality for arbitrary user poses is untested. I only used a walk clip, and the docs say out-of-distribution poses degrade.

## 6. Risks
- Do not run `uv sync`: run.sh:8-9 says it removes the manually installed tensorrt packages.
- The working tree already had modified .bvh files (LFS or line endings) before my run; I did not touch them.
- Plans are tied to GPU and TensorRT version, and the plan cache lives in `.trt-cache` relative to the working directory (default `cache_dir`).
- FP16 and FP32 diverge in token choice (mixed-precision caveat), and chaining amplifies it. Pick one for reproducibility.
- The output buffer is reused, so copy it before the next call (`.numpy().copy()`).
- NVIDIA Open Model Agreement for the weights; the sample BVH clips are evaluation-only (soma_model.md:38-41).

Throwaway files: probe.py, corr.py, logs and .npy outputs, and trt-cache/ (367 MB FP16 plan) in `.../reports/L1/`.
